# Plan: pairwise pacing, cheaper joins and protected coordination for the MLS key-exchange

This plan changes the key-exchange of the network-encryption (torii as MLS-client, izakaya as
MLS delivery service and coordinator). It is written to be worked through without any other
context: everything needed is described here or referenced by its path in this repository.

## 1. How the key-exchange works today

Read `docs/developer/sequence_diagrams/network_crypto_key_exchange.md` first; it describes all
flows. The short version:

- **hanami** signs membership-grants (`MlsGrant`, payload `MlsGrantPayload` with `vni`,
  `client_id`, `signature_key`, `action: Add | Remove`, `issued_at`, `expires_at`) and hands them
  to izakaya. Only a gateway with a grant may join the group of a network.
- **izakaya** (`src/binaries/izakaya/`) stores key-packages, delivers messages through a
  database-backed mailbox (`mls_messages`, every recipient gets its own copy, the gateway deletes
  it after processing), keeps one queue of operations per group (`mls_operations`) and one
  committer per group, and runs the *rounds*. All state is in its database, several instances
  can run in parallel. A background thread calls `tick` and `remove_dead_members` every second.
- **torii** (`src/binaries/torii/src/core/mls_key_exchange/`) is the MLS-client of a VM-host.
  Its identity (`client_id`) is the IPv4 underlay-address of the host. A background loop (the
  *agent*, `agent.rs`, every `POLL_INTERVAL` = 1 s) subscribes to the groups of its networks,
  executes operations as committer, processes messages and installs the derived keys in the
  kernel (XFRM, via `ip xfrm` in `src/binaries/torii/src/core/crypto.rs`). Its MLS-state is
  persisted in its database (`MlsState::save`, `src/binaries/torii/src/database/mls_storage_table.rs`),
  so a restart changes nothing for the group.

### Key derivation (`keys.rs`, unchanged by this plan)

- `derive_base`: `export_secret("ainari ipsec base v1", b"", 32)` of an epoch = *base secret*.
- `derive_sa`: HKDF-expand of the base secret with info
  `"ainari ipsec sa v1:{vni}:{src_vm}@{src_gw}->{dst_vm}@{dst_gw}"`, 40 bytes: 32 byte AES-256 key,
  4 byte GCM salt, 4 byte SPI (`| MLS_SPI_FLAG`). One SA per VM-connection and direction. Both
  ends derive the same SA, nothing is sent over the wire, the SPI needs no negotiation.
- `desired_connections`: every local VM of a network × every remote VM, which is reached over an
  encrypted route. A connection knows the underlay-address of the peer gateway
  (`peer_gateway_ip`), which is the `client_id` of the peer torii.
- `apply_network_keys`: installs incoming SAs first, then the outgoing SAs together with the
  atomic switch of the outbound policy (`activate_egress_key`, `ip xfrm policy update`), then
  removes what is not needed anymore. Without keys, the block policies keep an encrypted route
  fail-closed.

### Epochs and keys today (`state.rs`)

```rust
pub struct NetworkKeys {
    pub active_epoch: u64,                  // outgoing keys of ALL connections of the network
    pub bases: BTreeMap<u64, Vec<u8>>,      // incoming keys of every recorded epoch
    pub replaced: Option<ReplacedKeys>,     // keys of a group, which a new group replaced
}
```

- `record_epoch`: every new epoch (own commit merged in `deliver_and_merge`, processed commit in
  `agent.rs::handle_group_message`) is recorded, which installs its incoming keys for **all**
  connections.
- `reset_epochs` (joined a group), `replace_epochs` (joined/created a group, which replaces an
  older one, e.g. after izakaya lost its database).
- `activate` / `retire`: driven by the rounds.

### Rounds today (`izakaya/src/core/coordinator.rs`)

After every successful operation (`operation_done`) izakaya starts a round for the new epoch:
`Install` (members check, that they recorded the epoch, and ack) → `Switch` (members
`activate_epoch` and ack) → `Grace` (`CLEANUP_GRACE` = 2 s) → `Cleanup` (members
`retire_epochs`). Each phase waits for the acks of **all** members (`progress`); a phase without
progress for `STALL_TIMEOUT` (30 s) is given up. The next operation is only handed out after the
round. The torii side is `agent.rs::handle_round`.

### Operations today

- `subscribe` queues `Add` (with the grant), `store_grant` with `Remove` and `unsubscribe` and
  `remove_dead_members` (no contact for `member_timeout`, default 120 s) queue `Remove`, `tick`
  queues `Update` every `key_rotation_interval` (default 3600 s).
- `progress` hands **one** operation at a time to the committer (`send_operation`, message type
  `Operation`). The committer (`agent.rs::handle_operation`) makes one commit per operation
  (`group.rs`: `stage_add_member` with exactly one key-package, `stage_remove_member`,
  `stage_update`), delivers commit and welcome through izakaya, merges, and reports with
  `finish_mls_operation` (`MlsOperationDoneReq`).
- A re-add of a gateway, which lost its group, is a removal commit followed by an addition commit
  (`agent.rs::add_member`).
- Every member verifies the additions of a commit against the grants attached to the message
  (`group.rs::verify_additions`); a commit without matching grant is refused.

## 2. What is wrong with it

1. **Global barrier.** Every phase of a round waits for the slowest member. A silent gateway
   stalls every round for 30 s until it is removed after 120 s; a gateway, which refuses a commit,
   stalls the round of that epoch. Nothing else can happen in the group meanwhile.
2. **Expensive joins.** K gateways, which subscribe together (a new network with many VMs, the
   rebuild after izakaya lost its database), cost K commits one after another, each followed by a
   full round over all connections of the network. Every join rotates the keys of all pairs,
   although only the pairs with the new gateway need keys.
3. **Joins expose existing traffic.** Because a join moves every pair into the epoch of the join,
   the new gateway can derive the keys of all connections between the other gateways.
4. **Coordination is not protected.** The phases come from izakaya. A compromised izakaya can't
   read keys, but it can send `Switch` or `Cleanup` too early and so drop traffic.
5. **Old keys are removed by a timer.** `Cleanup` follows 2 s after the last `Switch` ack. A packet,
   which takes longer, is dropped; an idle network waits for nothing.

## 3. Target design

### Terms

- **Pair**: this gateway and one peer gateway in one network, key `(vni, peer)` with `peer` the
  `client_id` of the peer as `Ipv4Addr`. All VM-connections between the two gateways belong to
  the pair and change their keys together.
- **Epoch id**: `(generation, epoch)`. `generation` counts the groups of a network on this
  gateway; it is increased with every group, which is created or joined (`create_group`, a
  welcome). Epoch ids are compared as tuples, so the epochs of a newer group are always newer.
- **Pair epoch**: the epoch id, whose keys protect the outgoing traffic of a pair. It can lag
  behind the epoch of the group.
- **Target**: the epoch id, which a pair is moving to.

### 3.1 Key state per pair (torii, `state.rs`)

Replace `NetworkKeys` and `ReplacedKeys` by:

```rust
pub struct NetworkKeys {
    /// Generation of the current group of the network
    pub generation: u64,
    /// Base secrets by epoch id, kept as long as a pair references them
    pub bases: BTreeMap<(u64, u64), Vec<u8>>,
    /// The pairs of the network, by the client_id (underlay-address) of the peer
    pub pairs: BTreeMap<Ipv4Addr, PairKeys>,
}

pub struct PairKeys {
    /// Epoch id of the outgoing SAs towards the peer, None before the first switch
    pub egress: Option<(u64, u64)>,
    /// Epoch ids of the incoming SAs from the peer
    pub ingress: BTreeSet<(u64, u64)>,
    /// Epoch id, which the pair is moving to
    pub target: Option<(u64, u64)>,
    /// Latest Ready and Switched of the peer
    pub peer_ready: Option<(u64, u64)>,
    pub peer_switched: Option<(u64, u64)>,
    /// Latest Ready and Switched, which were sent to the peer
    pub ready_sent: Option<(u64, u64)>,
    pub switched_sent: Option<(u64, u64)>,
    /// Old incoming epochs, which wait for their removal, with the packet counters of their SAs
    /// at the last check (see 3.5)
    pub retiring: BTreeMap<(u64, u64), BTreeMap<u32, u64>>,
    /// The pair ends: its peer left the group, all its SAs are removed
    pub ending: bool,
    /// Pair of an older generation, whose peer didn't join the current group yet (see 3.8)
    pub stale_since: Option<i64>,
    /// Last error of a step, for the status (see 3.9)
    pub last_error: Option<String>,
}
```

- `bases` entries are removed, once no pair references the epoch id in `egress`, `ingress`,
  `target` or `retiring`.
- `MlsState` gets an outbox `pending_out: Vec<OutgoingMessage>` (Ready and Switched, which izakaya
  didn't accept yet) and a buffer `pending_in: Vec<MlsMessageResp>` (application messages of an
  epoch, which this gateway didn't reach yet). Both are persisted with the state.
- **No conversion of the persisted state**: a state in the old format fails in
  `MlsState::restore`, and `MlsState::load` already falls back to a fresh state, so torii joins
  its groups again with new keys. Nothing to implement.

`keys.rs::desired_sas` becomes per pair: for each connection, find the pair of its
`peer_gateway_ip`; derive the incoming SAs of all `pair.ingress` and `pair.retiring` epochs and
the outgoing SA of `pair.egress`. A connection without pair or without `egress` gets no outgoing
SA (fail-closed by the existing block policies). `apply_network_keys` keeps its order (ingress,
egress + policy switch, removal of the rest).

### 3.2 Which pairs a commit moves

Every commit (own commit after `merge_pending`, foreign commit after `merge_staged_commit`, a
joined welcome) is followed by one new function `apply_commit(vni, before, after)`, which replaces
`record_epoch`, `reset_epochs` and `replace_epochs`. `before` and `after` are the members of the
group as `client_id → signature-key of the leaf` (a re-added gateway has the same `client_id`, but
a new leaf, so a new signature-key).

The rule is derived only from the content of the commit, which MLS authenticates, so izakaya
can't influence it:

1. A peer, which is in `after` with a leaf, which was not in `before` (new or re-added gateway):
   its pair gets `target = (generation, new_epoch)`. This is unavoidable: the new leaf only knows
   the new epoch.
2. A peer, which is in `before` but not in `after` (removed gateway): its pair is `ending`.
3. **All** pairs get the new epoch as target, if the commit
   - removes a gateway, which is not re-added in the same commit (so a removed gateway can't
     use any key afterwards; this keeps the security property of today), or
   - adds and removes nobody (a pure self-update, i.e. the regular key-rotation).
4. Otherwise (only additions and re-adds), all other pairs keep their pair epoch.

After joining a group (welcome) or creating one, `generation` is increased and every pair with a
member of the new group gets the new epoch as target; pairs with peers, which are not in the new
group, are handled by 3.8.

Consequence of rule 4: a joining gateway can't derive the keys of the existing pairs, because they
stay on epochs, which it never had.

### 3.3 The steps of a pair

Run in the agent loop, for every pair with a target, after the messages were processed (new
function `drive_pairs`, called at the end of `run_once`). Every gateway runs the same steps:

1. **Ingress**: if `target ∉ ingress`: `ingress.insert(target)` and `apply_keys`. Only if the
   incoming SAs of all connections of the pair were installed without error, continue.
2. **Ready**: if `ready_sent != Some(target)`: queue `Ready{target}` for the peer (3.4) and set
   `ready_sent`.
3. **Egress**: if `peer_ready == Some(target)` and `egress != Some(target)`: set
   `egress = target` and `apply_keys` (installs the outgoing SAs and switches the policies
   atomically, then deletes the old outgoing SAs). On error, set `egress` back and retry with the
   next loop.
4. **Switched**: if `egress == Some(target)` and `switched_sent != Some(target)`: queue
   `Switched{target}` for the peer and set `switched_sent`.
5. **Old ingress**: if `peer_switched` is set: every epoch id in `ingress` older than
   `peer_switched` moves to `retiring`; their removal follows 3.5. When `target == egress` and
   `peer_switched >= target`, the pair has arrived: `target = None`.

An `ending` pair removes all its SAs right away (the peer is no member anymore) and is deleted.

Every step waits only for the own kernel and this one peer. A failing step is retried in the next
loop; `last_error` keeps the reason. Waiting is always safe: a pair, which doesn't move, keeps its
old keys, which still work on both ends.

A new target, while a pair is still moving, simply replaces the old one. The incoming SAs of the
old target stay in `ingress` until the peer switched to something newer, because the peer may
already send with them after the Ready. So the number of incoming epochs of a pair is at most
`1 + number of Readys not yet answered by a Switched`; commits are rare (operations, hourly
rotation), so no limit is needed. If it is needed later: don't send a new Ready, while more than
2 are unanswered.

`handle_round` and the round messages are removed (3.10).

### 3.4 Ready and Switched as MLS application messages

- New variant `MlsMessageType::Application` (string `"application"`), with `Display`, `FromStr`
  and the OpenAPI schema.
- Payload: an MLS `PrivateMessage` from `group.create_message(&provider, &signer, bytes)`, base64
  like the other MLS-messages (`group.rs::encode`). The plaintext is JSON:

  ```rust
  #[derive(Serialize, Deserialize)]
  pub struct PairMessage {
      pub kind: PairMessageKind,     // Ready | Switched
      pub generation: u64,
      pub epoch: u64,
      /// client_ids of the peers, which this message concerns
      pub peers: Vec<String>,
  }
  ```

  Put it into torii (`group.rs` or a new `pairs.rs`), not into the api-structs: izakaya never
  sees the plaintext.
- **Sending**: `drive_pairs` collects all Readys and all Switcheds of one epoch id into one
  message each, `recipients` = the peers concerned (not the whole group), `epoch` = the MLS epoch
  of the group at sending time. The messages go into `pending_out` and are handed to izakaya with
  `izakaya_clients::send_mls_message`; a message stays in `pending_out`, until izakaya accepted it.
- **Receiving** (`agent.rs::process_messages`, `group.rs::process_message`): process the MLS
  message; `ProcessedMessageContent::ApplicationMessage` → decode `PairMessage`.
  - The sender is `processed.credential()` → `client_id` (with `state.rs::identity_of`). The message only
    counts for the pair `(vni, sender)` and only, if the own `client_id` is in `peers`.
  - `generation` must be the current generation of the network, otherwise ignore it.
  - `peer_ready` / `peer_switched` are only replaced by a newer epoch id (replays and reordering
    change nothing; openmls refuses a message, whose key it already used, in addition).
- **Epochs**: `create_config()` and `join_config()` (`group.rs`) get `.max_past_epochs(16)`, so a
  Ready, which was encrypted shortly before a commit, can still be decrypted after it.
- **Messages of a future epoch**: if the MLS epoch of an application message is newer than the
  epoch of the group (its commit is not processed yet), keep it in `pending_in` and process it
  after the next commit of the group. Delete it at izakaya right away in any case (as today).
  Drop entries of `pending_in`, which are older than 16 epochs.
- After a restart nothing is sent twice: `ready_sent` / `switched_sent` are persisted, and
  `pending_out` is sent again.

### 3.5 Removal of old incoming keys without a timer

`CLEANUP_GRACE` is replaced by two observations, which torii makes on its own:

1. **The Switched of the peer** (step 5 of 3.3). The peer sends it only after its outgoing
   policies point at the new keys, so every packet with the old keys was handed to its kernel
   before the Switched was even created. Without a Switched, old incoming keys are never removed.
2. **The packet counters of the kernel.** When an epoch moves to `retiring`, read the packet
   counter of each of its incoming SAs of the pair and store it in `retiring`. In every following
   loop read them again; remove an SA, whose counter didn't change since the last read, and
   update the stored value of the others. When all SAs of a retiring epoch are removed, drop the
   epoch from `retiring`.

New function in `crypto.rs`:

```rust
/// Reads the number of packets, which an SA processed so far.
pub fn sa_packet_count(src: Ipv4Addr, dst: Ipv4Addr, spi: u32) -> Result<u64, String>
```

It runs `ip -s xfrm state get src {src} dst {dst} proto esp spi {spi:#x}` and parses the packet
count of the
`lifetime current:` block, which looks like `  1234(bytes), 56(packets)`. Check the exact output
of the iproute2 in the torii image (`dockerfiles/`) and add a unit test for the parser with a
captured sample. An SA, which doesn't exist anymore (e.g. after a host restart), counts as removed.
The existing helper `run_ip` (`src/binaries/torii/src/core/utils.rs`) only returns `Result<(),
String>`, so add a sibling `run_ip_output(args) -> Result<String, String>` there, which returns
stdout.

To keep this testable, `drive_pairs` gets the counter function as parameter (or a small trait),
so the tests can fake it.

So an idle pair loses its old keys in the loop after the Switched, and a pair, which still
receives packets with them, keeps them as long as they arrive. Only a single packet, which is
held back for more than a whole loop after the counter already stood still, is dropped.

The old **outgoing** SA is still deleted right after the policy switch, because the kernel uses
the new one for every new packet.

### 3.6 Batching of additions and removals

izakaya (`coordinator.rs`):

- New config `commit_delay` in `MlsConf` (milliseconds, default `1000`, one poll interval of the
  gateways). Document it in `izakaya_config.md`.
- `progress` no longer knows rounds. It only waits for an operation in flight (unchanged stall
  handling with `STALL_TIMEOUT`, retries and change of a dead committer). When nothing is in
  flight and the oldest queued `Add` or `Remove` is older than `commit_delay`, it takes **all**
  queued `Add` and `Remove` operations of the group (after the existing check for pointless
  operations) as one batch.
- `Update` is never merged into a batch with additions or removals (rule 3.2 recognizes a
  rotation by "adds and removes nobody"). A queued `Update` is handed out alone, when no `Add`
  or `Remove` is due. A removal moves all pairs anyway, so an `Update`, which is queued next to a
  batch with a removal, can be marked done with that batch.
- The committer is chosen as today: never the target of a removal or a re-add, preferring a
  living member (`pick_committer`).
- Table `mls_operations` gets a nullable column `batch_uuid VARCHAR(40)` (new migrations for
  sqlite and mysql, `table!` in `mls_operation_table.rs`, `izakaya_db.md`). All rows of a batch
  go in flight together with the same `batch_uuid` and `started_at`, and are retried, re-sent or
  finished together. Keeping one row per target keeps the deduplication in `enqueue` and
  `drop_queued_additions` working.
- Table `mls_groups` loses `round_epoch`, `round_phase`, `round_acks`, `round_updated_at` (new
  migration, `mls_group_table.rs`, `izakaya_db.md`). sqlite supports `ALTER TABLE ... DROP
  COLUMN`, the existing migration `2026-10-26-000001_remove_soft_delete` uses it already.

api-structs (`mls_structs.rs`):

```rust
pub struct MlsOperation {
    pub op_uuid: Uuid,                 // = batch_uuid
    pub vni: u32,
    /// Gateways to add (or to re-add, if still member), each with its grant
    pub adds: Vec<MlsOperationAdd>,    // { client_id: String, grant: MlsGrant }
    /// Gateways to remove
    pub removes: Vec<String>,
    /// Self-update of the committer (regular key-rotation), only without adds and removes
    pub update: bool,
}

pub struct MlsOperationDoneReq {
    pub op_uuid: Uuid,
    pub client_id: String,
    pub success: bool,
    pub epoch: u64,
    pub members: Vec<String>,
    pub reason: Option<String>,
    /// Gateways of the batch, which were left out, with the reason
    pub refused: Vec<MlsOperationRefusal>,   // { client_id: String, reason: String }
}
```

`MlsOperationKind` stays for the rows of `mls_operations`, but leaves the API.

`operation_done`: with `success`, record epoch and members and mark all rows of the batch done,
except the refused ones, which go back to `QUEUED` with `retries + 1` (or done after
`MAX_OPERATION_RETRIES`). Without `success`, keep today's behaviour for the whole batch
(including `drop_lost_members`). Then call `progress`, no round.

Committer (torii):

- `agent.rs::handle_operation` verifies every addition as `add_member` does today (grant via
  `verify_grant`, not expired, claim the key-package with the granted signature-key, check it).
  An addition, which fails, is left out and reported in `refused`; the others go on.
- New `group.rs::stage_change(state, vni, adds: Vec<(client_id, KeyPackage, MlsGrant)>,
  removes: Vec<String>)`: one commit with `group.commit_builder().propose_removals(...)
  .propose_adds(...).force_self_update(true).load_psks(storage)?.build(rand, crypto, signer,
  |_| true)?.stage_commit(provider)?`. Removals contain the old leaf of every re-added gateway
  (replaces the separate removal commit of `add_member`) and every gateway of `removes`, never
  the committer itself. Recipients of the commit: all members except the committer and the
  removed ones; one welcome to all added gateways; the grants of all added gateways are attached
  to the commit and the welcome (`OutgoingMessage.grants`).
- `stage_update` stays for `update: true`; `stage_add_member` and `stage_remove_member` are
  replaced by `stage_change`.
- `deliver_and_merge` calls `apply_commit` (3.2) instead of `record_epoch`.

Members (torii): `verify_additions` already checks every addition of a commit against the
attached grants; with several additions it has to accept a commit, where each addition is
covered by one of the grants. Add a test for a batch.

### 3.7 What izakaya can and can't do afterwards

| Coordination | Protected by | Checked by |
|---|---|---|
| Ready, Switched | MLS application message, signed by the leaf of the sender | the peer: sender is the gateway of the pair, own id in `peers`, newer epoch id |
| Which pairs move | content of the commit (3.2), authenticated by MLS | every member, on its own |
| Additions | grant of hanami attached to the commit (exists already) | committer and every member |
| Removals | nothing, izakaya decides | – |

- izakaya can **no longer drop traffic by timing**: switch and removal of keys depend only on the
  peer and the own kernel.
- izakaya can **still hold messages back**: the affected pairs stay on their old keys (safe) and
  key-rotations wait.
- izakaya can **still remove a gateway**. This can't be prevented, because only izakaya sees,
  which gateway is silent, and the removal of silent gateways is needed. The damage is limited:
  the removed gateway subscribes again with its grant (`RESUBSCRIBE_INTERVAL` = 30 s in
  `agent.rs`) and is added again, so it is an interruption of its connections, never a key. Every
  member logs every removal of a peer at level `warn` with the committer, so it can be audited.
- izakaya can **still skip the key-rotation** by never queueing `Update`. Members could detect
  this (no pure self-update for longer than the interval) and log it; optional, see section 6.

Update `docs/home/security_concpets.md` (row of izakaya and the section of the network
encryption) accordingly.

### 3.8 Replaced groups and pairs without peer

- A group, which replaces an older one (create after `reset_group`, welcome with
  `replaced: true`), is the next generation. Its pairs start with `target = (generation, epoch)`
  and keep the old keys (older generation) in `egress` / `ingress` until they moved, exactly like
  any rotation. `ReplacedKeys` and `replace_epochs` are removed.
- A pair, whose peer is no member of the current group (the peer didn't join the new generation
  yet), keeps its keys and gets `stale_since = now`. When the peer joins, its pair gets a target
  and `stale_since = None`. A pair, which is stale for longer than `STALE_PAIR_TIMEOUT` (new
  constant in torii, 120 s like `member_timeout`), ends: all its SAs are removed, its
  connections fall back to fail-closed.
- A pair, whose connections are all gone (routes deleted), keeps its state (cheap) and only loses
  its SAs, as today; it is deleted, when the peer leaves the group.

### 3.9 Status of the pairs

izakaya loses its view of the rounds, so torii gets an internal endpoint
`GET /v1alpha/network_crypto/mls/status/internal` (next to `/network_crypto/mls/identity/internal`
in `src/binaries/torii/src/api/routes/v1alpha.rs`, new file under
`src/binaries/torii/src/api/http_endpoints/network_crypto/`, response struct in
`ainari_api_structs::network_crypto_structs`). Per network and pair: `peer`, `egress`, `target`,
`ingress`, the step it waits on (`ingress`, `peer_ready`, `egress`, `peer_switched`,
`old_ingress_in_use`, `nothing`), `stale_since` and `last_error`. A client function for it goes into
`src/libs/rust/ainari_clients/src/network_crypto.rs`.

### 3.10 What is removed

- izakaya: `Round`, `RoundState`, `send_round`, `round_ack`, `CLEANUP_GRACE`, the round handling in
  `progress` and `operation_done`, the endpoint `ack_mls_round_internal_v1_0.rs` and its route
  `/mls_group/{vni}/round/internal`. `STALL_TIMEOUT` stays for operations only.
- api-structs: `MlsMessageType::Round`, `MlsRoundMessage`, `MlsRoundPhase`, `MlsRoundAckReq`,
  the fields `kind`, `client_id`, `grant` of `MlsOperation`.
- clients: `izakaya_clients::ack_mls_round`.
- torii: `handle_round`, `NetworkKeys::activate` / `retire`, `MlsState::activate_epoch` /
  `retire_epochs` / `record_epoch` / `reset_epochs` / `replace_epochs`, `ReplacedKeys`,
  `stage_add_member`, `stage_remove_member`, the removal commit in `add_member`.
- `remove_dead_members` stays: it no longer keeps the group moving, but it still cleans up.

## 4. Steps

Each step leaves a working system and ends with all checks of section 0 green. Steps are named
with letters (1a, 1b, ...) to keep them apart from the section numbers. Every step is reviewed
and committed by the human before the next one starts.

To keep the steps free of dead code (clippy), a new function is only added in the step, which
also calls it. The docs of izakaya config and database are updated in the step, which changes
them.

### Step 1a: one commit for several changes (torii)

Section 3.6, only the committer side, the API stays as it is.

- `group.rs::stage_change` (one commit with removals and additions) replaces
  `stage_add_member` and `stage_remove_member`. `handle_operation` calls it with one addition or
  one removal.
- `add_member`: the re-add is one commit (removal of the old leaf + addition), the separate
  removal commit is gone.
- `verify_additions` accepts a commit, where each of several additions is covered by one grant.
- Done when: a re-add is one commit; a commit with two additions and both grants is accepted by
  every member, with one grant missing it is refused (in-memory gateways, `group.rs` tests).

### Step 1b: operation API with lists (api-structs, izakaya, torii, clients)

Section 3.6, new `MlsOperation` / `MlsOperationDoneReq`, but izakaya still hands out one queued
row per operation. Protocol break.

- api-structs: `MlsOperation { op_uuid, vni, adds, removes, update }`, `MlsOperationAdd`,
  `MlsOperationRefusal`, `refused` in `MlsOperationDoneReq`; `MlsOperationKind` leaves the API.
- izakaya: `send_operation` maps the row to the new struct; `operation_done` puts refused rows
  back to `QUEUED` with `retries + 1` (done after `MAX_OPERATION_RETRIES`).
- torii: `handle_operation` works on the lists: verifies every addition, leaves the failing ones
  out and reports them in `refused`, commits the rest with `stage_change`.
- Done when: a missing key-package of one gateway of a batch doesn't stop the others (torii test
  with three in-memory gateways); a refused gateway is queued again (coordinator test).

### Step 1c: batch selection (izakaya)

Section 3.6, the rest of izakaya. The rounds stay: after a batch, `operation_done` starts one
round as today.

- `commit_delay` in `MlsConf` + `izakaya_config.md`.
- Migration `batch_uuid` (sqlite + mysql), `mls_operation_table.rs`, `izakaya_db.md`.
- `progress`: takes all due `Add` / `Remove` rows as one batch with one `batch_uuid` and
  `started_at`; retry, re-send, change of the committer and finish for all rows of the batch;
  `Update` alone, or marked done with a batch, which contains a removal.
- Done when: three gateways, which subscribe within `commit_delay`, get one operation; an
  `Update` is never in a batch with additions; a stalled batch is retried as a whole
  (coordinator tests).

### Step 2: key state per pair (torii)

Section 3.1, driven by the existing rounds: `Install` = every pair gets
the target, `Switch` = every pair switches, `Cleanup` = every pair drops its older incoming
epochs right away. No change in behaviour.

- `NetworkKeys { generation, bases, pairs }`, `PairKeys` with `egress`, `ingress`, `target` only
  (the other fields come with the steps, which use them), epoch ids `(generation, epoch)`.
- A replaced group is the next generation (section 3.8, first point); `ReplacedKeys` and
  `replace_epochs` are removed. Pairs of peers, which are not in the new group, are dropped at
  `Cleanup` (as `replaced` today).
- `keys.rs::desired_sas` per pair.
- Port the existing tests of `keys.rs` and `state.rs` to the new model.
- Done when: all existing tests pass in the new model.

### Step 3a: removal of old incoming keys by packet counters (torii)

Section 3.5, point 2, still triggered by `Cleanup`.

- `utils.rs::run_ip_output`, `crypto.rs::sa_packet_count` with a parser test on a captured
  output of the iproute2 of the torii image.
- `PairKeys.retiring`: `Cleanup` moves the older incoming epochs there instead of dropping them;
  the agent loop reads the counters and removes an SA, whose counter stood still. The counter
  function is a parameter (or small trait), so the tests can fake it.
- Done when: an old incoming SA stays as long as its faked counter rises and is removed in the
  first loop, in which it doesn't; an SA, which is gone in the kernel, counts as removed.

### Step 3b: Ready and Switched next to the rounds (api-structs, torii)

Section 3.4. The rounds still decide; the messages are only sent and recorded, so the transport
can be reviewed and tested on its own.

- `MlsMessageType::Application` (`Display`, `FromStr`, OpenAPI schema), `PairMessage`.
- `group.rs`: create and process application messages, `max_past_epochs(16)` in both configs.
- `MlsState`: `pending_out` (flushed in every loop), `pending_in` (messages of a future epoch,
  processed after the next commit, dropped after 16 epochs), both persisted.
- `PairKeys`: `ready_sent`, `switched_sent`, `peer_ready`, `peer_switched`.
- `handle_round` additionally queues a `Ready` after `Install` and a `Switched` after `Switch`
  for every pair; received messages update `peer_ready` / `peer_switched` with the checks of
  section 3.4 (sender, own id in `peers`, generation, only newer).
- Done when: a Ready, which arrives before its commit, is processed after the commit; a Ready of
  another sender or without the own id in `peers` is ignored; a replayed older Ready changes
  nothing; a message stays in `pending_out`, until izakaya accepted it.

### Step 3c: pairs move on their own (torii)

Section 3.3 and 3.5, point 1. Every commit still moves all pairs (section 3.2 comes in step 4).

- `drive_pairs` at the end of `run_once`, with the five steps of section 3.3 and `last_error`.
- Every recorded epoch becomes the target of all pairs right away (not at `Install`).
- `handle_round` only acks the phases (so izakaya keeps working until step 3d), it no longer
  changes keys or sends messages.
- Done when: a gateway, which never answers, only blocks its own pairs, the pairs between the
  others move; a restart between Ready and Switched (save, load into a new `MlsState`)
  continues without sending anything twice; without a Switched, old incoming keys are never
  removed; "without a gap" holds at every moment (as the `keys.rs` tests check it).

### Step 3d: removal of the rounds (izakaya, api-structs, clients, torii)

Section 3.10, mostly removing code. Protocol break.

- izakaya: `Round`, `RoundState`, `send_round`, `round_ack`, `CLEANUP_GRACE`, round handling in
  `progress` and `operation_done`, the endpoint and route `/mls_group/{vni}/round/internal`;
  migration, which drops the round columns of `mls_groups` (sqlite + mysql),
  `mls_group_table.rs`, `izakaya_db.md`.
- api-structs: `MlsMessageType::Round`, `MlsRoundMessage`, `MlsRoundPhase`, `MlsRoundAckReq`.
- clients: `ack_mls_round`.
- torii: `handle_round`, `activate` / `retire` / `activate_epoch` / `retire_epochs`.
- Coordinator tests: round helpers removed, the round tests rewritten to "the next operation
  follows right after `operation_done`".
- Done when: no round state is left, all tests pass.

### Step 3e: stale pairs (torii)

Section 3.8, second and third point. Until this step, a pair, whose peer is not in the current
group, is dropped with the first commit of the new group.

- `PairKeys.stale_since`, `STALE_PAIR_TIMEOUT`, `ending`.
- Done when: a replaced group (`generation + 1`) moves every pair without a gap; a pair, whose
  peer doesn't join, keeps its keys and ends after `STALE_PAIR_TIMEOUT`.

### Step 4: commit rule (torii)

Section 3.2 (`apply_commit`) and the `warn` log of every removal of a peer (section 3.7). From
here on, additions only move the new pairs.

- `apply_commit(vni, before, after)` replaces `record_epoch` and `reset_epochs`.
- Done when: a join of C doesn't change any SA between A and B; a removal moves every remaining
  pair and afterwards no SA of an epoch known to the removed gateway is left; a pure
  self-update moves every pair.

### Step 5a: status of the pairs (api-structs, torii, clients)

Section 3.9.

- Response struct, endpoint `GET /v1alpha/network_crypto/mls/status/internal`, client function.
- Done when: a test of the computation of the waiting step for every case.

## 6. Decisions taken, and open questions

Taken, so the work isn't blocked; change them only with a reason:

- `commit_delay` = 1000 ms, `max_past_epochs` = 16, `STALE_PAIR_TIMEOUT` = 120 s.
- No limit on unanswered Readys per pair.
- Rule 3.2 is fixed in the code, not configurable: removals and pure self-updates move all pairs,
  additions only the new ones.
- The removal of a gateway stays unproven (3.7).

Open, to be answered by the human (note them in the summary, don't block on them):

- Should members log a warning, when no pure self-update came for longer than
  `key_rotation_interval` (sign of an izakaya, which skips rotations)? The members don't know the
  interval today; it would need a torii config value.
- Reading the counters with `ip -s xfrm state get` costs one process per SA and loop while an
  epoch retires. If that is too much on hosts with many connections, read them over netlink
  instead (new dependency).
- New VM-connections: the outgoing SA of a new connection is installed right away with the pair
  epoch (as today with the active epoch). If the receiver didn't get its route yet, the first
  packets are dropped. Unchanged by this plan.
